# Labellerr SDK / platform feedback (friction log)

Written while building this, in the order I hit things. SDK version: `labellerr-sdk`
1.3.2, installed from source (`github.com/Labellerr/SDKPython`, commit `37b56ff`, 2026-10-23).

| # | What happened | Suggested improvement |
|---|---|---|
| 1 | `pip install labellerr-sdk` finds nothing on PyPI. The README's install line points to a `labellerr_sdk-1.0.0.tar.gz` release, but `pyproject.toml` on `main` says 1.3.2. | Publish to PyPI (or at least keep the README install link on the current version). |
| 2 | README examples use `from labellerr.client import LabellerrClient` with **two** args `(api_key, api_secret)` and `client.initiate_create_project(...)` / `client.upload_preannotation_by_project_id(...)`. In 1.3.2 the client takes **three** args `(api_key, api_secret, client_id)`, and these operations are module functions (`labellerr.core.projects.create_project`, `LabellerrProject.upload_preannotations`). | Generate the README from the current docstrings, or add a "migrating from 1.0" section. |
| 3 | The credentials story is unclear: the README says "contact support for api_key and client_id" while the client needs key + secret + client id. I started with only client id + secret and got `401 Invalid Authorization Header – No authorization token was found`, which doesn't say *which* header is missing. | Validate the constructor (`api_key must be non-empty`) and return "missing api_key header" from the API. |
| 4 | `upload_preannotations` sends the **api_key** as an `email_id` header (`extra_headers={"email_id": self.client.api_key}`). It looks like a leftover from the old email-based auth. | Drop it, or take a real `email` argument. |
| 5 | `upload_preannotations(conf_bucket=...)` accepts `low/medium/high` (checked with `assert`, which disappears under `python -O`), but nothing explains what a bucket does on the platform (a filter? a queue? does it affect review routing?). This is exactly the feature a confidence-based review workflow needs, so it should be documented. | Document the semantics and show where buckets appear in the UI; raise `LabellerrError` instead of `assert`. |
| 6 | `bulk_assign_files(file_ids, new_status)`: `new_status` is a free string with no list of valid values in code or docs. | Expose an enum of file statuses (e.g. `FileStatus.REVIEW`). |
| 7 | The SDK has no tags / custom metadata write API for files, even though `LabellerrFile.metadata` exists for reading. | Add `file.set_metadata({...})` / tags, so pipelines can attach "why flagged" reasons per file. |
| 8 | Docs conflict on the pre-annotation format: examples use `annotation_format="coco_json"`, while the troubleshooting section says `'coco'`. The SDK only accepts `json`, `coco_json`, `csv`, `png`. | Make the docs match `constants.ANNOTATION_FORMAT`. |
| 9 | The pre-annotation docs say COCO categories / attributes must match the template, but don't say how a COCO **category name** maps to a template **question** (I assume question text == category name, one bbox question per class). | Add a worked "template ↔ COCO categories" example for multi-class bounding boxes. |
| 10 | `labellerr/core/schemas.py` and the package `labellerr/core/schemas/` both exist. The package wins, so the `.py` file is dead code with duplicate, slightly different models (e.g. two `ListFileParams`). | Delete the shadowed module. |
| 11 | `project.list_files()` returns a raw dict whose shape isn't documented; I had to search it for `file_id`/`file_name`. There is no "get file by name" helper, which every pre-annotation pipeline needs. | Return `LabellerrFile` objects plus a pager, and add `project.get_file_by_name()`. |
| 12 | Free-plan rotation limits (`RotationConfig(1,1,1)` only) and the `dataset.status()` wait before `create_project` are only mentioned in docs prose; skipping the wait gives a confusing "has no files" error. | Have `create_project` wait / retry, or give an explicit "dataset still processing" error. |
| 13 | **Name collision:** `labellerr.core.schemas` exports two different `CreateTemplateParams` (from `schemas.projects` and `schemas.annotation_templates`); the package-level one is the *projects* variant. Following the docs (`from labellerr.core.schemas import *` + `create_template(...)`) fails with `4 validation errors for CreateTemplateParams: client_id Field required; questions.0 Input should be ... Question`. Workaround: import from `labellerr.core.schemas.annotation_templates`. | Rename one of them (e.g. `CreateProjectTemplateParams`) and add a test that runs the docs snippet. |
| 14 | Values pasted into env settings with a trailing `;` (`LABELLERR_CLIENT_ID=16252;`) are silently sent as-is. | Strip / validate credential format in the client constructor. |
| 15 | `project.list_files(search_queries={})`: the SDK's pydantic schema accepts a dict (and its own integration tests pass `{}`), but the API returns `400 Validation Error: search_queries – Input should be a valid list`. | Make the schema `List[...]` only and fix the tests. |
| 16 | **File search silently returns nothing for a while.** About 3 min after the run (~11:55 UTC; dataset `files_count == 100`, dataset attached, both pre-annotation jobs `completed`), `project.list_files(search_queries=[])` returned `total_count: 0`. At the same time the web UI showed the project with **100 files: Annotation 98 (96 left, 2 in progress), Review 2, 0 accepted**. So my pipeline couldn't resolve a `file_id` and the `bulk_assign_files` trial never ran. Re-checked at ~12:04 UTC: the same call returned all 100 files, so it looks like an indexing / eventual-consistency delay, but neither the SDK nor the docs say so, and an empty result looks exactly like "no files". | Document the delay and expose readiness (e.g. `project.wait_until_searchable()`, or have `list_files` signal "index not ready" instead of returning 0). |
| 17 | **The API key is stored as the file's `email_id`.** On 96 of the 100 project files, `list_files` returns `email_id` equal to the API key (the other 4 had been opened in the web UI). This follows from #4 (`upload_preannotations` sends `email_id: api_key`). It means the key is shown to anyone who can list the project's files. | Treat as a security bug: stop sending the key as `email_id`, and scrub existing records. |
| 18 | `list_files` items carry the workflow status in a field called `status` (values seen: `'None'` as a string for untouched files, `assigned`, `cr_assigned`), while the SDK's export code filters on `id: "file_status"`, and the UI shows different labels ("Annotation / Review / Accepted"). There's no documented mapping between API statuses and UI columns. | Publish the status enum and its UI mapping; return `None` rather than the string `'None'`. |
| 19 | **`conf_bucket` has no visible effect in the UI.** Both uploads (`low` for 62 flagged images, `high` for 32 auto-accepted) returned `completed`, and the boxes appear in the Label tool as ⚡ suggestions under *AI Mode / Model Assisted* (confidence slider, accept/reject). But I couldn't find anywhere in the UI that shows, filters or queues files by bucket, and neither the SDK nor the docs explain what the bucket does. For a confidence-based review workflow, it's the one feature that should make flagged images stand out. | Show the bucket as a file-list filter / queue (or tag), document it, and expose it in `list_files`. |
